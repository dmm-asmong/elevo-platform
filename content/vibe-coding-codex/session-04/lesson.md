# 4회차 — GitHub 저장 + Vercel 배포

> **오늘의 핵심 메시지:** ==변경마다 되돌릴 수 있는 지점을 이유와 함께 남기고, 그 기록을 온라인에 두고, 기록을 그대로 공개 주소로 바꾼다==

---

## 🗂 지금까지의 저장 방식이 막히는 지점

2·3회차에 만든 결과물을 파일로만 저장하면 이런 일이 생긴다.

- `소개.html` → `소개_수정.html` → `소개_진짜최종.html` — 어느 것이 최신인지 파일 이름만으로는 알 수 없다.
- 무엇이 왜 바뀌었는지 남지 않는다. 며칠 지나면 본인도 이유를 기억하지 못한다.
- 이전 상태로 정확히 되돌릴 수 없다. 덮어쓴 뒤에는 기준점이 사라진다.
- 남에게 보여줄 주소가 없다. 고칠 때마다 파일을 다시 보내야 한다.

오늘은 ==GitHub==에 작업을 올리고 ==Vercel==로 배포해서, 이 네 가지 문제를 한 번에 해결한다.

## 🔑 Git과 GitHub은 다른 것

가장 자주 헷갈리는 지점이다. 표로 정리한다.

| | Git (2005) | GitHub (2008) |
|---|---|---|
| 정체 | 파일 변경을 추적하는 **버전 관리 도구** | Git 프로젝트를 클라우드에 올려두는 **플랫폼** |
| 어디서 동작하나 | 내 컴퓨터에서 실행되는 프로그램 | 인터넷 서비스 |
| 하는 일 | 언제 무엇을 왜 바꿨는지 저장 지점으로 기록 | 그 기록(저장소)을 호스팅하고 배포와 연결 |
| 인터넷 | 없어도 기록할 수 있다 | 필요하다 |

> **핵심 문장: GitHub 없이 Git은 쓸 수 있지만, Git 없이 GitHub은 쓸 수 없다.**
> 오늘 쓰는 `commit`(커밋), `push`(푸시), `git revert`는 전부 Git의 기능이고, GitHub은 그 결과가 도착하는 장소다.

### 📖 용어 정리

| 용어 | 쉬운 풀이 |
|------|-----------|
| **저장소 (repository)** | 프로젝트별 온라인 공간. 주소에 계정명과 저장소명이 표시된다 |
| **커밋 (commit)** | 어떤 상태를 왜 남겼는지 기록한 저장 지점. 나중에 비교하고 복구하는 기준점 |
| **푸시 (push)** | 내 컴퓨터의 확인된 변경을 GitHub 저장소에 반영하는 작업 |

### GitHub에 올리면 따라오는 네 가지

| 용도 | 내용 |
|---|---|
| **되돌리기** | 잘못된 변경만 골라 취소한다. 전체를 다시 만들지 않는다 |
| **기록** | 언제 무엇이 왜 바뀌었는지가 남는다 |
| **배포의 입구** | !!Vercel 같은 배포 서비스는 Git 저장소를 기준으로 동작한다!! 올려두면 자동 배포와 롤백이 연결된다 |
| **공개 주소** | `github.com/사용자이름` 자체가 결과물 목록이 된다 |

세 번째가 오늘 GitHub을 거치는 진짜 이유다. Vercel에 파일을 바로 올리지 않고 GitHub을 거치는 건, Vercel이 Git 저장소를 기준 삼아 배포·재배포·롤백을 자동화하도록 만들어진 서비스이기 때문이다. GitHub은 백업 장소가 아니라 ==배포 파이프라인의 입구==다.

## 👤 가입(GitHub)과 설치(Git)는 다른 일

"GitHub에 가입했는데 왜 또 뭘 깔아야 하지?" — 계정을 만드는 것과 프로그램을 설치하는 것은 완전히 다른 작업이다.

| | 무엇인가 | 어디에 있나 | 해야 할 일 |
|---|---|---|---|
| GitHub 계정 | 인터넷 서비스의 계정 | GitHub 회사의 서버 | 가입으로 끝 |
| Git | 내 컴퓨터에서 실행되는 프로그램 | 내 노트북 | **따로 설치해야 함** |

오늘 Codex에게 "GitHub에 올려 줘"라고 요청하면, Codex가 직접 파일을 전송하는 게 아니다. Codex는 내 컴퓨터에서 `git` 명령을 대신 실행할 뿐이고, 실제로 기록(`commit`)하고 전송(`push`)하는 건 Git이라는 프로그램이다. !!Codex 안에 Git이 들어 있지는 않다!!.

### 1단계 — GitHub 가입 + 이메일 인증

1. 브라우저에서 `github.com/signup`을 연다.
2. 이메일, 비밀번호, 사용자 이름을 입력하거나 Google 계정으로 가입한다.
   - 사용자 이름은 저장소 주소(`github.com/사용자이름/저장소이름`)에 그대로 공개되니, 실명·생년월일·전화번호 같은 개인정보는 넣지 않는다.
3. 가입 후 받은 인증 메일의 링크를 누른다.
4. 우측 상단 프로필 사진 → `Settings` → `Emails`에서 `Verified` 표시를 확인한다.
5. 우측 상단 `+` → `New repository`를 눌러 저장소 생성 화면이 열리면 가입이 끝난 것이다.

### 2단계 — Git 설치 확인

가입 확인이 끝나면 Codex에게 이렇게 물어본다.

```prompt
git --version을 실행해서 결과만 알려주세요. 다른 작업은 하지 마세요.
```

- `git version 2.45.1.windows.1`처럼 버전 번호가 나오면 준비 완료다.
- `The term 'git' is not recognized...`가 나오면 Git이 없거나, 설치 후 앱을 다시 시작하지 않은 상태다.

설치가 필요하면 Codex에게 확인부터 시킨다.

```prompt
내 컴퓨터에 Git이 설치되어 있는지 확인해 주세요.

- 설치되어 있으면 버전만 알려주고 아무것도 바꾸지 마세요.
- 설치되어 있지 않으면 Windows에서 설치하는 방법을 안내만 하고,
  실행은 하지 말고 기다려 주세요.
- 설치를 마친 뒤 이 앱을 다시 시작해야 하는지도 함께 알려주세요.
```

> !!설치 직후에는 Codex 앱을 완전히 종료했다가 다시 열어야 `git` 명령이 인식된다!!. 프로그램은 시작할 때 한 번만 시스템 경로(PATH)를 읽기 때문이다.

## 🧹 배포할 프로젝트 준비하기

1. 배포할 프로젝트를 하나 고른다 — 2회차 소개 사이트(기본 권장) 또는 3회차 게임.
2. 고른 프로젝트 폴더를 두 번 복사해 `본인프로젝트명-manual`, `본인프로젝트명-codex`로 이름을 나눈다. 같은 작업을 두 가지 방법으로 올려보기 위해서다.
3. 대표 HTML 파일 이름을 **`index.html`**로 맞춘다.
   - 주소 최상단(`/`)에는 `index`라는 이름의 파일이 있어야 그 파일이 바로 열린다. 다른 이름이면 파일 목록 화면이 뜨거나 404 오류가 난다.
4. 두 폴더 모두 `index.html`, `README.md` 두 파일만 남긴다.
5. `index.html`을 더블클릭해 브라우저에서 정상적으로 열리는지 확인한다.
6. API 키, 비밀번호, 개인정보, `.env` 파일이 없는지 확인한다.

> 업로드 전에는 항상 사람이 먼저 파일 실체와 공개 가능 여부를 확인한다. AI의 답변만 믿고 공개하지 않는다.

## 📤 방법 A — GitHub 웹에서 직접 올리기

1. GitHub 우측 상단 `+` → `New repository`.
2. 저장소 이름에 `본인프로젝트명-manual`을 입력하고, 공개 범위는 `Public`으로 둔다.
3. `Add a README file` 등 초기화 옵션은 선택하지 않는다.
4. `Create repository` → 새 저장소 화면에서 `Add file` → `Upload files`.
5. `index.html`, `README.md`를 끌어다 놓고, 커밋 메시지에 `첫 프로젝트 업로드`를 입력한 뒤 `Commit changes`.

**사람이 직접 확인:** 저장소 주소에 내 사용자 이름과 `-manual`이 보이는가? 공개 범위가 `Public`인가? 파일이 두 개뿐이고 내용이 정상인가?

## 🤖 방법 B — Codex에게 GitHub 업로드 요청하기

Codex에게 곧바로 "올려줘"라고 하지 않는다. **빈 저장소 준비 → 사전 확인 → 계획 검토 → 실행 요청 → 웹에서 결과 확인** 순서를 지킨다.

### 1단계. 빈 저장소를 먼저 만든다

방법 A와 같은 방식으로 `본인프로젝트명-codex` 저장소를 **빈 상태로** 만든다(초기화 옵션 선택 안 함). 저장소를 먼저 사람이 만들어 두면 Codex가 할 일이 "내 파일을 지정된 주소로 보내기" 하나로 좁아진다.

### 2단계. Codex에서 `본인프로젝트명-codex` 폴더를 연다

`-manual` 폴더를 잘못 열지 않았는지 먼저 확인한다.

### 3단계. 사전 확인 프롬프트

```prompt
현재 프로젝트를 아직 GitHub에 올리지 말고 다음만 확인해 주세요.
빈 저장소는 제가 GitHub 웹에서 이미 만들어 두었습니다. 새 저장소를 만들지 마세요.

1. 현재 작업 폴더 이름과 경로
2. index.html과 README.md가 실제 존재하는지
3. 개인정보, 비밀번호, API 키, .env 파일이 없는지
4. git --version 결과와 현재 폴더의 Git 저장소·origin 연결 여부
5. Git 사용자 이름·이메일 설정 여부 (실제 push 권한은 지금 확인할 수 없으니 추측하지 마세요)
6. 실행할 작업 순서와 업로드될 파일 목록

기존 저장소나 origin이 발견되면 덮어쓰지 말고 알려주세요.
확인 결과를 보여준 뒤 실행하지 말고 기다려 주세요.
```

**계획을 검토할 때 볼 것:** 현재 폴더가 `-codex`인가? `git --version`이 정상인가? 업로드 목록이 두 파일뿐인가? 기존 저장소나 `origin`을 덮어쓰려 하지 않는가?

### 4단계. 실행 프롬프트

```prompt
확인한 계획대로 현재 프로젝트를 아래 저장소에 올려 주세요.

대상
- 원격 저장소: https://github.com/[사용자이름]/[본인프로젝트명]-codex.git
- 기본 브랜치: main

작업 조건
- index.html과 README.md만 포함할 것
- 기존 파일 내용은 수정하지 말 것
- 새 저장소를 만들지 말고 위 주소에만 연결할 것
- 기존 origin이 이미 있으면 덮어쓰지 말고 멈추고 알려줄 것
- 인증이 필요하면 브라우저 로그인 방법을 안내하고 멈출 것
- push 직전에 연결된 주소와 보낼 파일 목록을 다시 보여줄 것

완료 후 저장소 URL, 커밋 ID, 브랜치, 업로드된 파일 목록과 현재 상태를 보고해 주세요.
```

이 요청을 받으면 Codex는 `git init` → `git add` → `git commit` → `git remote add origin` → `git push` 순서로 작업한다. !!모두 내 컴퓨터에 설치된 Git이 실행하는 명령이고, Codex는 그 명령을 대신 실행하고 결과를 읽어 주는 역할이다!!.

### 5단계. 결과를 직접 확인한다

Codex의 "완료했습니다"라는 답변만으로 끝내지 않는다. 저장소 주소를 직접 열어 소유자·이름·공개 범위·최신 커밋·파일 내용을 눈으로 확인한다.

### 두 방법 비교

| 항목 | GitHub 웹 수동 업로드 | Codex 요청 업로드 |
|---|---|---|
| 파일 보내기 | 브라우저에서 끌어다 놓기 | 내 컴퓨터의 Git이 `commit`·`push` 실행 |
| 필요한 준비 | 브라우저만 있으면 됨 | Git 설치와 push 인증이 필요 |
| 반복 수정 | 매번 직접 반영 | 수정·검토·커밋·푸시를 한 흐름으로 지시 가능 |

> 웹 업로드는 오늘 한 번으로 끝난다. 이후 수정과 재배포부터는 Codex 방식만 쓴다.

## 🔗 Codex Cloud에 GitHub 연결하기

"GitHub 연결"이라고 부르는 것은 보통 Codex Cloud와 GitHub 저장소를 잇는 기능을 말한다.

1. Codex에서 Cloud 또는 환경 설정 화면을 연다.
2. `Connect GitHub`를 선택하고 GitHub 승인 화면에서 연결할 계정을 확인한다.
3. 가능하면 `Only select repositories`로 `본인프로젝트명-manual` 저장소만 허용한다.
4. Codex로 돌아와 그 저장소를 선택한 환경을 만든다.
5. 새 작업에서 확인한다.

```prompt
현재 연결된 저장소 이름과 보이는 파일 목록을 알려주세요. 파일은 수정하지 마세요.
```

### 세 가지 연결을 헷갈리지 않기

| 구분 | 무엇을 연결하는가 | 역할 |
|---|---|---|
| Codex Cloud GitHub 연동 | Codex 환경 ↔ 이미 존재하는 GitHub 저장소 | 저장소를 읽고 작업 환경을 구성 |
| 로컬 GitHub 인증 | 내 컴퓨터의 Git ↔ GitHub 계정 | 내 변경을 `push`할 권한 확인 |
| Vercel GitHub 연동 | Vercel 프로젝트 ↔ GitHub 저장소 | 커밋 후 자동 재배포 |

> **중요:** Codex Cloud에서 GitHub를 연결했다고 해서 내 컴퓨터의 로컬 `push` 인증까지 자동으로 끝나는 것은 아니다. 세 가지는 각각 따로 연결해야 한다.

## 🚀 Vercel에 배포하기

1. Vercel에 GitHub 계정으로 로그인한다.
2. `Add New` → `Project`를 누르고 `본인프로젝트명-codex` 저장소를 선택한다.
3. 프레임워크 자동 감지 결과를 확인하고 `Deploy`를 누른다.
4. 배포 주소를 열어 확인한다.
   - [ ] 페이지가 오류 없이 열린다
   - [ ] 핵심 제목이 보인다
   - [ ] 버튼이나 주요 상호작용이 작동한다
   - [ ] 모바일 폭에서도 핵심 내용이 잘리지 않는다

## 🔄 수정하고 자동 재배포 확인하기

### 1) 수정 요청

```prompt
index.html의 첫 화면에 "4회차 배포 확인 완료" 문구를 추가해 주세요.

조건:
- 기존 디자인과 기능은 유지할 것
- 먼저 변경 계획과 대상 위치를 설명하고 기다릴 것
- 승인 후 파일을 수정할 것
- 수정한 위치와 diff를 요약할 것 (브라우저에서 여는 확인은 제가 직접 합니다)
- 내가 확인하기 전에는 commit 또는 push하지 말 것
```

### 2) 확인 후 반영

```prompt
로컬 확인을 마쳤습니다. 현재 변경분만 커밋하고 main 브랜치에 push해 주세요.

- 커밋 메시지: 배포 확인 문구 추가
- 다른 파일은 포함하지 말 것
- 완료 후 커밋 ID와 push 결과를 알려줄 것
```

push하면 Vercel이 새 커밋을 감지해 자동으로 다시 배포한다. GitHub의 최신 커밋 → Vercel 배포 상태 → 실제 배포 URL 순서로 직접 확인한다.

## ⏪ 잘못된 커밋 되돌리기

기록을 지우지 않고 되돌리는 방법이 `git revert`다.

```prompt
최근 커밋 목록을 보여주고, "배포 확인 문구 추가" 커밋의 ID와 변경 파일을 알려주세요.
아직 되돌리거나 push하지 마세요.
```

대상 커밋을 사람이 직접 확인한 다음 되돌린다.

```prompt
방금 확인한 "배포 확인 문구 추가" 커밋만 git revert로 되돌려 주세요.

- 기존 커밋 기록을 삭제하거나 강제 push하지 말 것
- 생성될 revert 커밋의 내용을 먼저 설명하고 기다릴 것
- 승인 후 revert하고 main에 push할 것
- 완료 후 새 커밋 ID와 변경 파일을 알려줄 것
```

==`git revert`는 기록을 삭제하지 않고, "되돌렸다"는 새 기록을 추가하는 방식==이다. 그래서 무엇을 왜 되돌렸는지도 그대로 남는다.

## 🧯 자주 생기는 문제

| 문제 | 확인 순서 |
|---|---|
| `git`을 찾을 수 없다는 오류 | Git 설치 → Codex 앱 완전히 종료 후 재시작 → `git --version` 재확인 |
| `push`가 거부됨(rejected) | 저장소를 만들 때 README나 `.gitignore`를 함께 만든 경우다. 저장소를 지우고 빈 상태로 다시 만든다 |
| Codex Cloud에 저장소가 안 보임 | GitHub 계정 → 저장소 접근 범위 → 조직 승인 여부 확인 |
| 이미 Git 저장소 또는 origin이 있음 | 덮어쓰지 말고 기존 연결의 소유자와 주소부터 확인 |
| Vercel에 저장소가 안 보임 | Vercel의 GitHub 접근 권한에서 `-codex` 저장소 허용 여부 확인 |
| 배포 화면이 이전 상태임 | 최신 GitHub 커밋 → Vercel 배포 상태 → 브라우저 새로고침 순서로 확인 |
