# 2회차 — 마이크로 PRD로 완성하는 1페이지 브랜드 랜딩페이지

> **오늘의 핵심 메시지:** ==기획서 없이 만들면 AI가 폭주한다. 기획이 곧 코딩이다.==

---

## 📑 PRD란 무엇인가?

### "AI 에이전트의 헌법"이 된 기획서

**PRD(Product Requirements Document, 제품 요구사항 명세서)**는 소프트웨어를 만들기 전에 ==무엇을(What), 누구를 위해(Who), 왜(Why) 만드는지==를 정의하는 문서다.

전통적인 IT 조직에서는 프로덕트 매니저(PM)가 PRD를 작성하면 디자이너·개발자·QA가 그것을 읽고 각자 코드를 짰다. 그런데 바이브 코딩 시대에는 **Codex 같은 AI 에이전트가 PRD를 읽고 10초 만에 코드를 작성**한다. 그래서 PRD는 이제 사람이 읽는 보고서가 아니라, ==AI가 제멋대로 폭주하지 못하게 막는 가드레일==이 됐다.

### 왜 50페이지가 아니라 "마이크로 PRD"인가

과거의 방대한 기획서는 작성에만 몇 주가 걸리고 비개발자가 쓸 수도 없었다. 게다가 AI에게 너무 긴 문서를 주면 앞뒤 맥락을 놓치는 문제가 생긴다. 그래서 핵심만 1~2페이지 마크다운(`PRD.md`)으로 압축한 **==마이크로 PRD==**를 쓴다.

### 📖 용어 정리

| 용어 | 쉬운 풀이 |
|------|-----------|
| **PRD** | 무엇을, 누구를 위해, 왜 만드는지 정리한 기획 문서 |
| **마이크로 PRD** | 핵심만 1~2페이지로 압축한 PRD. 단일 마크다운 파일로 관리 |
| **Out-of-Scope** | 이번 버전에서 절대 만들지 않을 것을 명시한 항목 |

---

## 🧭 마이크로 PRD 4대 핵심 구조

```
1. Problem & Goal  : 누구의 어떤 문제를 해결하는가?
2. User Flow       : 방문자가 어디를 보고 어디를 클릭하는가?
3. Key Features    : 핵심 3대 기능은 무엇인가?
4. Out-of-Scope    : 이번 버전에서 만들지 않을 것 (★핵심)
```

### 왜 "제외 범위"가 가장 중요한가

AI에게 불필요한 기능까지 섞어서 지시하면 집중력이 분산돼 완성도가 떨어진다. 반대로 ==**"로그인 없음, 결제 없음, 관리자 페이지 없음"**을 먼저 못 박으면== AI는 남은 부분(디자인·핵심 기능)에 온전히 집중한다. "무엇을 만들지"만큼 "무엇을 만들지 않을지"를 정하는 것이 중요하다.

---

## 🤖 AI 인터뷰로 PRD 15분 완성하기

백지에 혼자 기획서를 쓰려면 막막하다. 그래서 AI에게 **"수석 PM" 역할**을 맡기고, 내 아이디어 한 줄을 듣고 객관식 질문(A/B/C)을 던지게 만든다. 나는 몇 번 고르기만 하면 된다.

### 📖 용어 정리

| 용어 | 쉬운 풀이 |
|------|-----------|
| **동적 적응형 인터뷰** | AI가 내 답변을 보고 다음 질문을 스스로 조정하는 방식 |
| **CoT (Chain-of-Thought)** | 한 번에 다 만들지 않고, 단계를 하나씩 밟아가며 점진적으로 완성하는 방식 |

### 🤖 PRD 인터뷰어 마스터 프롬프트

```prompt
너는 실리콘밸리 15년 경력의 베테랑 수석 프로덕트 매니저(Lead PM)야.
내가 만들고 싶은 웹 서비스의 거친 아이디어를 말하면, 코딩이 가능한 완벽한 [마이크로 PRD (Product Requirements Document)]를 완성할 수 있도록 나를 1:1 인터뷰해줘.

[오늘 결과물의 고정 제약 - 질문하지 말고 그대로 반영]
- 결과물은 서버와 데이터베이스 없이 브라우저에서 바로 열리는 단일 HTML 파일 1개다.
- 1차 제외 범위는 이미 확정됐다: 회원가입·로그인 / 온라인 결제 / 관리자 대시보드 / 다국어 / 실제 메일이 전송되는 문의 폼.
- 위 5가지를 PRD의 [제외한 내용] 항목에 그대로 옮겨 적고, 다른 어떤 항목에도 넣지 말 것.

[인터뷰 진행 규칙 - 엄격 준수]
1. 한 번에 여러 질문을 쏟아내지 말고, 반드시 질문을 1개씩만 던질 것.
2. 질문을 할 때는 내가 비개발자라도 쉽게 고를 수 있도록 [추천 보기 3가지(A, B, C)]를 항상 구체적으로 제시해줄 것.
3. 내 답변을 바탕으로 기획에 꼭 필요한 3대 요소(타깃의 핵심 고통, 사용자 흐름, 핵심 3대 섹션)를 스스로 판단하여 다음 질문으로 자연스럽게 이어갈 것.
4. 총 3~4회의 문답이 끝나 정보가 충분히 모이면, 추가 질문을 멈추고 최종 기획 내용을 정리하여 반드시 [docs/PRD.md] 파일로 직접 저장해줄 것.

내가 만들고 싶은 서비스 아이디어는 다음과 같아:
"[ 여기에 내가 만들고 싶은 아이디어 1줄 입력 ]"

위 아이디어를 분석하고, 첫 번째 질문과 추천 보기 3가지를 제시해줘!
```

### PRD 파일 확인 체크리스트

AI가 `docs/PRD.md`를 저장했다고 답해도 ==항상 눈으로 직접 확인==한다.

1. 파일이 실제로 생겼는가?
2. 내가 말한 적 없는 엉뚱한 내용이 들어가진 않았는가?
3. 내가 꼭 넣고 싶던 핵심 내용이 빠지진 않았는가?
4. `제외한 내용`에 5가지(로그인·결제·관리자·다국어·문의 폼)가 그대로 적혔는가?

빠진 게 있으면 짧게 한 줄로 다시 요청하면 된다: `"제외한 내용에 ○○도 넣어 주세요."`

## 🧱 웹페이지는 세 겹으로 되어 있다

웹페이지는 하나의 덩어리가 아니라 **세 장이 겹쳐진 것**이다. 오후에 "이거 고쳐줘"라고 할 때, 어느 층을 고칠지 말할 수 있으면 한 번에 원하는 결과가 나온다.

| 겹 | 이름 | 맡은 일 | 이 겹을 지우면 |
|---|---|---|---|
| 1층 | **HTML** | 무엇이 있는가 (제목·문단·버튼·이미지) | 아무것도 남지 않는다 |
| 2층 | **CSS** | 어떻게 보이는가 (색·크기·여백·배치) | 내용은 남지만 흑백 목록처럼 보인다 |
| 3층 | **JavaScript** | 누르면 무엇이 일어나는가 (클릭·열림·계산) | 보이긴 하는데 눌러도 반응이 없다 |

| 요청 문장 | 어느 겹? |
|---|---|
| "제목 문구를 바꿔줘" | 내용 · **HTML** |
| "배경을 남색으로, 글자를 더 크게 해줘" | 디자인 · **CSS** |
| "버튼을 누르면 창이 뜨게 해줘" | 동작 · **JavaScript** |

!!AI는 "예쁘게 해줘"보다 "어느 층을, 어떻게"를 알아듣는다.!! 세 겹을 구분할 수 있게 된 순간, 요청은 두 배 정확해진다.

## 🎯 고객을 설득하는 랜딩페이지 구조

### 4단 구조

```
1. Hero 섹션      : 첫 화면에서 이탈을 막는 강렬한 헤드카피 + 메인 버튼
2. 3대 Feature 카드 : 고객이 얻을 3가지 구체적 이득
3. FAQ / 후기      : 망설이는 심리적 장벽 제거
4. Final CTA       : 화면 하단, 단 하나의 명확한 신청 버튼
```

### 60:30:10 컬러 황금 비율

| 비율 | 역할 | 예시 |
|---|---|---|
| **60%** | 배경/베이스 | 차분하고 신뢰감을 주는 배경색 |
| **30%** | 카드/컨테이너 | 콘텐츠를 돋보이게 하는 카드 영역 |
| **10%** | 강조 액센트 | ==오직 CTA 버튼과 배지에만== 사용해 시선을 집중시킴 |

## 🛠 실습 — PRD로 랜딩페이지 완성하기

### Step 1. 계획을 파일로, 그다음 코드로

```prompt
이 계획에 동의합니다. 이 계획과 와이어프레임을 docs/PRD.md 파일로 먼저 저장해 주세요.
그다음 이 계획대로 모바일 반응형 index.html을 만들어 주세요.
HTML·CSS·JavaScript를 이 파일 하나에 모두 포함해 주세요.
```

파일이 생기면 `index.html`을 더블클릭해서 브라우저로 열어 기본 구조(Hero, 3대 카드, CTA)가 보이는지 확인한다. 에러가 나면 당황하지 말고 브라우저의 개발자 도구(F12) 콘솔에 뜨는 에러 메시지를 그대로 복사해 AI에게 붙여넣는다 — **"어떤 행동을 했더니, 무엇을 기대했는데, 실제로는 무엇이 일어났다"** 세 가지만 전달하면 충분하다.

### Step 2. 내용(HTML)만 고치기

```prompt
index.html의 내용만 고쳐 주세요. 디자인과 동작은 지금 그대로 두세요.
맨 위 제목과 한 줄 소개를 제 계획표의 문구로 바꾸고,
가운데 카드 3칸의 제목과 설명도 제 계획표의 핵심 내용으로 바꿔 주세요.
고치기 전에 어디를 어떻게 바꿀지 먼저 알려 주세요.
```

### Step 3. 디자인(CSS)만 고치기

```prompt
index.html의 디자인만 고쳐 주세요. 글의 내용과 동작은 그대로 두세요.
전체 분위기를 제 계획표의 디자인 테마에 맞춰 주시고, 강조색은 문의 버튼 하나에만 써 주세요.
화면이 좁아지면 카드 3칸이 세로 1칸으로 자연스럽게 바뀌게 해 주세요.
고치기 전에 어디를 어떻게 바꿀지 먼저 알려 주세요.
```

### Step 4. 동작(JavaScript)만 고치기

```prompt
index.html의 동작만 고쳐 주세요. 글과 디자인은 그대로 두세요.
문의 버튼을 눌렀을 때 연락 방법이 나타나는 것은 지금처럼 유지하고,
한 번 더 누르면 다시 접히게 해 주세요.
고치기 전에 어디를 어떻게 바꿀지 먼저 알려 주세요.
```

한 번에 한 겹씩만 지목해서 수정하면, 문제가 생겨도 방금 고친 겹만 되돌리면 되기 때문에 실패 확률이 크게 줄어든다.

## 🚀 심화 도전 — 틀에 박힌 AI 디자인 벗어나기

AI에게 "예쁘게 만들어줘"라고만 하면 항상 비슷한 파란 버튼과 밋밋한 박스만 나온다. AI는 가장 안전한 평균치 템플릿을 내놓기 때문이다. 명확한 디자인 레퍼런스를 쥐어주면 결과가 달라진다.

### 방법 A — 마음에 드는 화면 캡처해서 스타일 복제하기

Pinterest, Dribbble 등에서 마음에 드는 레이아웃을 캡처(`Win + Shift + S`)한 다음:

```prompt
첨부한 캡처 이미지의 디자인 스타일을 분석해줘.
1. 배경색, 본문 텍스트색, 포인트 강조색(HEX 코드)
2. 카드의 둥글기(border-radius)와 그림자 깊이
3. 전체적인 여백감과 폰트 분위기

내용과 기존 버튼 동작은 지금 index.html 그대로 두고,
오직 디자인 스타일만 이 캡처의 무드와 동일하게 리디자인해줘.
바꾸기 전에 분석한 디자인 규칙을 먼저 3줄로 요약해줘.
```

### 방법 B — `DESIGN.md`로 디자인 규칙을 문서화하기

"기능의 헌법이 `PRD.md`라면, ==디자인의 헌법은 `DESIGN.md`==다." 컬러 팔레트·폰트·여백·둥글기 규칙을 별도 문서로 저장해두면, 다음에도 같은 스타일을 일관되게 유지할 수 있다.

```prompt
내 작업 폴더의 DESIGN.md 파일을 읽어봐.
거기에 정의된 컬러 팔레트, 폰트, 여백, 카드 둥글기와 그림자 규칙을
현재 index.html의 디자인에 전면 적용해줘.
글 내용과 기존 버튼 클릭 동작은 하나도 건드리지 말고, 디자인 시스템만 완벽히 동기화해줘.
```

## 📱 모바일 반응형 검수 & 작업 기록

브라우저에서 `F12` → `Ctrl + Shift + M`을 눌러 모바일 화면으로 전환하고, 가로 스크롤 없이 카드가 세로 1열로 떨어지는지 확인한다.

오늘의 작업 기록도 손으로 쓰지 않고 AI에게 맡긴다.

```prompt
오늘 우리가 나눈 대화 전체를 돌아보고 day02_log.md 파일을 만들어 주세요.
다음 네 부분으로 나눠서 정리해 주세요.
1. 진행 과정: 계획표를 만든 순서와 페이지를 고친 순서를 시간 흐름대로.
2. 결과 및 주요 판단: 계획표에서 무엇을 넣고 무엇을 제외하기로 했는지, 그리고 왜 그렇게 정했는지.
3. 배운 점과 인사이트: HTML, CSS, JavaScript가 각각 무엇을 담당하는지 제 답변에서 드러난 이해를 한 문장씩.
4. 다음 실습에 적용할 나만의 원칙: 오늘 실제로 통했던 요청 방식을 제 말투로 세 줄.
```

---

## ✅ 오늘의 핵심 정리

1. **마이크로 PRD** = 무엇을 만들지, 그리고 ==무엇을 만들지 않을지==를 정하는 1~2페이지 기획서.
2. **AI 인터뷰 기법** = 백지에서 혼자 고민하지 않고, AI가 던지는 객관식 질문에 답하며 기획을 완성한다.
3. **세 겹 구분** = 수정 요청은 항상 "내용(HTML) / 디자인(CSS) / 동작(JS)" 중 어느 겹인지 지목한다.
4. **한 겹씩 점진적 수정(CoT)** = 한 번에 다 고치려 하지 않는다. 한 겹씩 수정하면 실패해도 되돌리기 쉽다.
