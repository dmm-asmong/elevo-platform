# 7회차 — 나만의 "교육자료" Skill 만들기

> **오늘의 핵심 메시지:** ==반복되는 작업은 Skill로 묶고, 한 번뿐인 일은 프롬프트로 처리한다==

---

## 🧰 Skill이란?

### 매번 다시 설명하지 않아도 되는 이유

지금까지는 원하는 결과를 매번 길게 설명해왔다.

```text
생성형 AI의 환각을 초보 성인에게 설명하는 교육자료를 만들고,
출처를 조사하고, 5장으로 개요를 짜고, 내가 확인한 뒤,
한 파일짜리 HTML 슬라이드로 만들고, 모바일에서도 보이게 해줘...
```

**Skill**을 한 번 만들어두면 다음부터는 이렇게 짧게 불러도 같은 순서와 품질이 유지된다.

```prompt
$education-slide-maker

생성형 AI를 처음 배우는 성인에게
AI의 환각과 확인 방법을 설명하는 5장 자료를 만들어 주세요.
```

> ==Skill은 AI에게 반복해서 설명하던 작업 순서와 기준을 저장한 재사용 가능한 작업 설명서다.==

### 와플 기계 비유

- **일반 프롬프트 복사·붙여넣기** — 매번 손으로 반죽을 빚어 굽는 것과 같다. 매 대화마다 길게 설명해야 하고, 실행할 때마다 결과 품질이 들쭉날쭉해진다.
- **Skill** — AI에게 규격화된 !!"와플 기계(작업 틀)"!!를 꽂아주는 것과 같다. 딸기 반죽이든 초코 반죽이든(주제가 바뀌어도) 같은 규격(정확히 5장, 단일 HTML, 모바일 대응)을 안정적으로 유지한다.

한 번만 할 일(예: "지금 이 화면만 한 번 다듬어줘")은 Skill로 만들지 않고 그냥 프롬프트로 처리한다. ==Skill은 "앞으로도 반복할 일"에만 만든다.==

### 📖 용어 정리

| 용어 | 쉬운 풀이 |
|------|-----------|
| **Skill** | AI에게 저장해두는 재사용 가능한 작업 설명서. 이름을 불러 실행한다 |
| **SKILL.md** | Skill 폴더에 반드시 있어야 하는 파일. 이름·설명·작업 순서가 담겨 있다 |
| **시맨틱 라우팅** | AI가 수십 개의 Skill 중 지금 요청에 어떤 Skill을 꺼내 써야 할지 `description`을 읽고 판단하는 것 |

---

## 📁 Skill 폴더 구조

```text
skill-name/
├── SKILL.md          필수 — 이름·설명·작업 순서
├── agents/            선택 — 화면에 어떻게 보여줄지 정보
├── scripts/           선택 — 매번 반복 실행할 코드
├── references/        선택 — 필요할 때만 꺼내 보는 참고 문서
└── assets/            선택 — 완성본에 들어갈 재료 파일
```

오늘 만들 `education-slide-maker`처럼 지침이 짧은 Skill은 ==`SKILL.md` 한 장으로 충분==하다. `scripts/`·`references/`·`assets/`는 반드시 필요한 게 아니다.

### SKILL.md 작성 규칙

| 필드 | 규칙 |
|------|------|
| `name` | 소문자·숫자·하이픈만 사용, 64자 이내, **폴더 이름과 반드시 같아야 함** |
| `description` | 무엇을 하는지 + 언제 쓰는지까지 담아야 함 (AI가 이 설명을 읽고 어떤 Skill을 꺼낼지 판단한다) |

| 좋은 `description` | 나쁜 `description` |
|---|---|
| "교육 주제와 대상을 받아 자료 조사·5장 개요·승인 후 HTML 슬라이드 제작을 이어줄 때 사용한다." | "교육 자료를 도와주는 스킬" |

약병에 '소화제'라고 명확히 쓰지 않고 '좋은 약'이라고만 써두면 필요할 때 꺼내 쓸 수 없는 것과 같다. ==언제 작동해야 하는지를 명확히 적어야 AI가 제때 찾아 쓴다.==

### 저장 위치

| 범위 | 언제 쓰는가 |
|------|-------------|
| **전역** (내 계정 전체) | 어떤 프로젝트를 열어도 항상 쓸 도구 — "나만의 만능 도구함" |
| **프로젝트** (이 저장소 전용) | 이 프로젝트를 여는 사람만 쓰는 도구, 팀과 공유할 때 |

정확한 저장 경로는 Codex 버전에 따라 달라질 수 있으므로, !!항상 설치 직후 AI가 알려주는 경로를 그대로 확인한다.!! 오늘처럼 어떤 프로젝트에서도 쓸 만한 Skill은 전역에 두는 것이 자연스럽다.

## 🛠 실습 1 — 나만의 Skill 만들기

원하는 결과와 순서를 짧게 말하면, AI가 Skill 파일을 만들고 저장 위치를 알려준다.

```prompt
$skill-creator

교육 주제와 교육 대상만 말하면
자료 조사, 5장 슬라이드 개요 작성,
단일 HTML 슬라이드 제작까지 도와주는
education-slide-maker Skill을 만들어 주세요.

개요를 보여준 뒤에는 제 확인을 받고
HTML을 만들도록 해주세요.

초보자가 사용할 Skill이므로
부족한 정보는 쉬운 보기로 질문하게 해주세요.
```

### ✅ 즉시 검토

- AI가 알려준 위치에 `education-slide-maker/SKILL.md`가 실제로 생성되었는가?
- `name`이 `education-slide-maker`인가? (폴더 이름과 일치하는지도 확인)
- `description`에 교육자료 조사·5장 개요·HTML 제작 용도가 드러나는가?
- 조사 → 5장 개요 → 사람 승인 → HTML 순서인가?

빠진 게 있으면 이렇게 보완을 요청한다.

```prompt
방금 만든 Skill에서 빠진 규칙만 보완해 주세요.
조사 → 5장 개요 → 제 승인 → HTML 순서를 지키고,
승인 전에는 HTML을 만들지 않게 해주세요.
```

---

## 🚦 왜 중간에 "승인" 단계를 둘까? — 인간 승인 루프

처음부터 "조사해서 5장 HTML 슬라이드 바로 만들어줘"라고 한 번에 시키지 않고, 굳이 개요 단계에서 멈춰 사람의 확인을 받는 이유가 있다.

- 짧은 텍스트 **개요** 단계에서 내용을 고치는 것은 설계도에 연필로 지우개질하는 것처럼 ==변경 범위가 작고 확인하기 쉽다.==
- 수백 줄 코드로 완성된 **HTML** 단계에서 구조를 바꾸면 CSS·JavaScript·화면 전환까지 영향을 받아 되돌리기 어렵고 검토 비용이 커진다.

그래서 코드를 만들기 직전, 사람이 설계도를 최종 확정하는 지점을 반드시 둔다. AI가 조사와 제작을 맡아도 아래 세 가지는 항상 사람이 결정한다.

1. 조사 내용이 교육 대상과 수준에 맞는가?
2. 5장 흐름에서 빠지거나 불필요한 내용은 없는가?
3. 이 개요로 HTML을 만들어도 되는가?

## 🚀 실습 2 — 실제 주제로 실행하기

```prompt
$education-slide-maker

생성형 AI를 처음 배우는 성인을 대상으로
AI의 환각과 확인 방법을 설명하는
5장 교육 슬라이드를 만들어 주세요.
```

### 조사 결과 검토 — 출처를 눈으로만 훑지 않는다

오늘 주제가 "AI의 환각"인데, 정작 조사를 맡은 AI 자신이 ==존재하지 않는 가짜 링크나 논문을 그럴듯하게 지어내는 환각==을 일으킬 수 있다. AI가 달아준 출처 링크는 브라우저 새 탭에 직접 복사해 넣어 **실제로 열리는지** 확인해야 한다. 링크가 열리지 않으면 그 내용은 즉시 삭제하고 쓰지 않는다.

### 개요 검토와 수정

정확히 5장인지, 한 장에 핵심 메시지가 하나인지, 사례가 눈높이에 맞는지 확인한다.

```prompt
3장의 사례가 너무 어렵습니다.
직장이나 일상에서 겪을 수 있는 예로 바꿔 주세요.
아직 HTML은 만들지 말아 주세요.
```

개요가 적절할 때만 승인한다.

```prompt
이 개요로 HTML 슬라이드를 만들어 주세요.
```

### HTML 스모크 테스트

1. 파일이 실제로 만들어졌는지 확인한다.
2. 더블클릭해 브라우저에서 연다.
3. 정확히 5장인지 확인한다.
4. 방향키(←→)와 화면 버튼으로 처음부터 끝까지 이동해본다.
5. 브라우저 폭을 좁혀 글자가 겹치거나 잘리지 않는지 본다.

## 🔍 공개 Skill을 설치하기 전에 확인할 것

공개 Skill은 설치만으로 끝나지 않는다. 실행하면 AI 에이전트가 그 지침에 따라 파일을 수정하거나 명령을 실행할 수 있다. ==출처와 내용을 확인하지 않고 실행하면 소스코드 손상이나 정보 노출 위험이 생길 수 있다.== 설치 전 아래 다섯 가지를 먼저 물어본다.

1. 누가 공개했는가?
2. 무엇을 하는가?
3. 내 원본 파일을 수정하거나 명령을 실행하는가?
4. 추가 설치나 로그인이 필요한가?
5. 사용 조건을 적은 라이선스 파일이 있는가?

```prompt
이 공개 Skill을 처음 사용하는 비개발자입니다.

1. 누가 공개했는지
2. 무엇을 하는지
3. 내 파일을 수정하거나 명령을 실행하는지
4. 추가 설치나 로그인이 필요한지
5. 라이선스 파일이 있는지 쉬운 말로 알려주세요.

아직 설치하지 말아 주세요.

Skill 주소:
https://github.com/anthropics/skills/tree/main/skills/frontend-design
```

답변이 불분명하면 이렇게 한 번 더 물어본다.

```prompt
방금 설명에서 제가 설치 전에 꼭 알아야 할 위험이나 변경 사항만 다시 알려주세요.
```

확인이 끝났으면 설치를 요청한다. 이때도 !!"오늘 허용할 범위"!!를 명확히 적는 것이 핵심이다 — 안전한지 여부를 Skill 이름이 아니라 이번 요청의 범위로 통제한다.

```prompt
$skill-installer

frontend-design Skill을 설치해 주세요.
출처: https://github.com/anthropics/skills/tree/main/skills/frontend-design

지금은 설치만 하고 제 프로젝트 파일은 건드리지 마세요.
설치 결과와 다음 대화에서 사용하는 방법만 쉬운 말로 알려주세요.
```

### 📖 용어 정리

| 용어 | 쉬운 풀이 |
|------|-----------|
| **위협 모델** | 이 도구를 쓸 때 어떤 방식으로 문제가 생길 수 있는지 미리 따져보는 것 |
| **최소 권한의 원칙** | 필요한 범위만 허용하고, 나머지는 막아두는 안전 원칙 |

## 🎨 실습 3 — frontend-design으로 화면 다듬기

`frontend-design`은 이전 회차에서 만든 웹앱의 메인 화면을 계층·타이포·여백·대비·정렬 기준으로 다듬어주는 공개 Skill이다.

| 좋은 부탁 | 나쁜 부탁 |
|---|---|
| "메인 화면만 다듬어 줘. 검색·결과 카드 기능은 그대로 둬." | "처음부터 더 예쁘게 다시 만들어 줘." |
| "먼저 계획만 보여 줘. 실행해 주세요 하면 수정." | "알아서 다 고치고 배포까지." |

적용할 때 지킬 원칙:

1. 메인 화면만 다듬는다 (기능 전체를 다시 만들지 않는다).
2. 기존 기능은 그대로 유지한다.
3. 지도·로그인·새 라이브러리 추가는 하지 않는다.
4. 계획을 먼저 확인하고, "실행해 주세요"라고 답한 뒤에만 수정하게 한다.

```prompt
$frontend-design 스킬을 사용해서 지금 프로젝트의 메인 화면만 개선해 주세요.

목표:
- 첫눈에 "완성된 서비스"처럼 보이게
- 여백, 타이포, 계층, 카드/버튼 대비를 정리
- 모바일에서도 읽기 쉽게

꼭 지키기:
- 기존 기능·버튼·동작은 그대로
- 파일을 통째로 새로 만들지 말고 지금 화면을 수정
- 지도, 로그인, 새 라이브러리 추가 금지

작업 전에 바꿀 곳을 쉬운 말로 3~5줄 계획만 보여 주고,
내가 "실행해 주세요"라고 한 뒤에만 수정하세요.
끝난 뒤 전후 차이를 3줄로 요약해 주세요.
```

버튼이 깨졌을 때는 디자인이 아니라 동작만 고쳐 달라고 요청한다 (이 요청에는 `$frontend-design`을 쓰지 않는다).

```prompt
디자인은 더 바꾸지 마세요.
지금 깨진 동작만 최소로 고쳐 주세요.
- 어떤 버튼:
- 기대한 동작:
- 실제 동작:
```

### 적용 결과 검토

1. 여백·글자 위계·버튼 대비가 실제로 개선됐는지 확인한다.
2. 기존 버튼과 기능이 여전히 동작하는지 직접 클릭해본다.
3. 화면 표현만 바뀌었는지, 기능 코드까지 통째로 다시 만들어지지 않았는지 훑어본다.

---

## ✅ 오늘의 핵심 정리

1. **Skill** = 반복할 작업의 순서와 기준을 저장해 짧게 불러 쓰는 작업 설명서. 한 번뿐인 일에는 만들지 않는다.
2. **`description`이 핵심** = 무엇을·언제 하는지 명확히 적어야 AI가 제때 꺼내 쓴다.
3. **승인 지점이 안전장치** = 개요 단계에서 멈춰 확인하면, 완성된 코드를 되돌리는 것보다 훨씬 쉽게 방향을 바로잡을 수 있다.
4. **공개 Skill은 설치 전 확인** = 누가·무엇을·내 파일을 건드리는지·추가 설치가 필요한지부터 물어본다.
5. **출처는 직접 클릭해 확인** = AI가 붙여준 링크도 그대로 믿지 않는다.

## ➡️ 다음 단계

오늘 만든 두 가지 습관 — ==직접 만든 Skill을 실행해보는 것==과 ==공개 Skill을 안전하게 확인하고 쓰는 것==은 앞으로 어떤 프로젝트를 만들 때도 그대로 재사용할 수 있다.

시간이 남으면 `education-slide-maker`를 다른 주제로 다시 실행해보거나, `frontend-design`을 이전 회차에서 만든 다른 화면에 적용해보자. 무엇을 바꿨는지 한두 줄로 기록해두면 나중에 다시 꺼내 쓰기 좋다.
