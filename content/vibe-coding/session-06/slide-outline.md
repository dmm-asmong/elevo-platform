* 강사 유의사항: 코드 파일을 잃어버린 학생이 있으면 기획서+디자인 프롬프트를 다시 AI에 입력해서 빠르게 복구하도록 안내. 5분 이내로 모든 학생이 5회차 결과물을 확보하게 한다.
슬라이드 4 이론 — 기능(로직)이란? (이론 페이지)
* 소요시간: 이론 10분 중 전반부
* 웹앱의 3가지 구성 요소 복습:
* HTML = 뼈대 (화면에 뭐가 있는지: 제목, 버튼, 입력창 등)
* CSS = 옷 (어떻게 보이는지: 색상, 크기, 배치 등)
* JavaScript = 뇌 (어떻게 동작하는지: 버튼을 누르면 뭐가 일어나는지)
* 오늘 집중할 것: JavaScript, 즉 "기능(로직)"을 AI에게 만들어달라고 하는 것
* "기능"이란 구체적으로 뭘까?
* "버튼을 클릭하면 → 결과가 화면에 나타난다"
* "입력창에 글을 쓰고 엔터를 누르면 → 목록에 추가된다"
* "드롭다운에서 선택하면 → 선택한 값에 맞는 내용이 보인다"
* "날짜를 입력하면 → 오늘부터 그 날짜까지 남은 일수를 계산한다"
* 즉, "사용자가 ~하면 → ~이 일어난다"가 기능의 핵심 패턴
* 쉬운 풀이 박스:
* 로직(Logic) = 프로그램이 동작하는 규칙과 순서. "만약 A이면 B를 해라" 같은 것
* 함수(Function) = 특정 기능을 수행하는 코드 묶음. "이 버튼을 누르면 이 함수가 실행된다"
* 이벤트(Event) = 사용자가 하는 행동. 클릭, 입력, 스크롤 등
* 프로토타입(Prototype) = 완성품 전 단계의 시제품. "일단 핵심 기능은 돌아가는 상태"
슬라이드 5 이론 — 에러는 실패가 아니라 대화의 시작 (이론 페이지)
* 소요시간: 이론 10분 중 후반부
* 디버깅(Debugging)이란?
* 코드에서 버그(오류)를 찾아서 고치는 것
* 이름의 유래: 옛날 컴퓨터에 진짜 벌레(bug)가 들어가서 오작동한 것에서 유래
* 바이브 코딩에서의 디버깅: 코드를 직접 읽을 필요 없이, 에러 메시지를 AI에게 보여주면 AI가 고쳐줌
* 에러가 나면 어떻게 해야 할까? — 3단계 디버깅법:
* 1단계: 브라우저에서 에러 메시지 확인하기
* 화면이 하얘지거나 버튼이 안 눌리면 → 크롬에서 F12 키 누르기 → "Console(콘솔)" 탭 클릭 → 빨간 글씨가 에러 메시지
* 또는 화면에 직접 에러 내용이 표시되는 경우도 있음
* 2단계: 에러 메시지를 통째로 복사하기
* 빨간 글씨를 드래그해서 선택 → Ctrl+C로 복사
* 3단계: AI에게 에러 메시지를 보여주고 수정 요청하기
* 프롬프트: "이 코드를 실행했더니 아래 에러가 나왔어. 원인을 찾아서 수정해줘. 에러 메시지 붙여넣기"
* AI가 수정된 코드를 주면 → 다시 저장 → 다시 실행 → 확인
* 핵심 마인드:
* 에러는 실패가 아니라 AI와 대화할 새로운 주제가 생긴 것!
* 에러 없이 한 번에 완벽하게 되는 경우가 오히려 드물다
* "에러 → 수정 → 확인 → 에러 → 수정 → 확인"을 반복하는 것이 정상적인 개발 과정
* 완벽주의를 버리자 — "충분히 좋은(good enough)" 상태면 OK. 나머지는 나중에 개선
* 쉬운 풀이 박스:
* 디버깅(Debugging) = 코드의 오류(버그)를 찾아서 고치는 과정
* 콘솔(Console) = 브라우저에 숨어있는 개발자 도구. 에러 메시지가 여기에 표시됨. F12 또는 Ctrl+Shift+J로 열 수 있음
* 에러 메시지(Error Message) = 코드에 문제가 있을 때 컴퓨터가 알려주는 경고문. 무슨 에러인지, 어디에서 발생했는지 알려줌
* 점진적 개발(Incremental Development) = 기능을 한꺼번에 다 만들지 않고, 하나씩 추가하며 확인하는 방식
슬라이드 6 이론 — 기능 요청 프롬프트 전략 (이론 페이지)
* 기능을 AI에게 요청할 때의 핵심 전략: "한 번에 하나씩!"
* 나쁜 예: "모든 기능 다 넣어줘" → 코드가 길어지고 에러 가능성 높아짐
* 좋은 예: "먼저 기능 1만 구현해줘" → 확인 → "잘 되면 기능 2 추가해줘" → 확인 → ...
* 이것이 바로 점진적 개발(Incremental Development) 또는 점진적 커밋(Incremental Commits)
* 기능 요청 프롬프트 패턴:
지금 이 웹앱 코드에 아래 기능을 추가해줘.
기능: 사용자가 ~하면 → ~이 일어난다
조건:
* 기존 디자인(색상, 레이아웃, 폰트)은 절대 바꾸지 마
* 기존에 동작하던 기능도 깨뜨리지 마
* HTML, CSS, JavaScript를 하나의 파일에 유지해줘
* "기존 것을 건드리지 마"라는 조건이 매우 중요!
* AI에게 기능 추가를 요청하면, 가끔 기존 디자인이나 다른 기능을 바꿔버리는 경우가 있음
* "기존 코드는 유지하고, ~만 추가해줘"라고 명시하면 이 문제를 줄일 수 있음
슬라이드 7 이론 → 실습 전환 (강사용 교안)

* AI 리터러시 포인트: "오늘 에러를 만나면 축하할 거예요. 에러를 만난다는 건 뭔가를 시도했다는 뜻이니까요. 진짜 실패는 에러가 나는 게 아니라, 에러가 무서워서 시도를 안 하는 거예요. 에러 메시지를 복사해서 AI에게 던지면 AI가 다 고쳐줍니다. 여러분은 에러를 고칠 필요 없어요. AI에게 제대로 보고하기만 하면 됩니다."
* 강사 시연 (2분): 강사가 직접 일부러 에러가 나는 상황을 만들고, F12 → 콘솔 → 에러 메시지 복사 → AI에게 전달 → 수정 코드 받기 과정을 빠르게 시연

슬라이드 10 실습 1 — 에러가 났을 때 대처법 (실습 페이지)
* 에러 상황별 대처 가이드:
* 상황 1: 화면이 아예 하얗게 나온다
* F12 → Console 탭 → 빨간 에러 메시지 확인 → 전체 복사
* AI에게: "이 코드를 실행하면 화면이 하얗게 나와. 콘솔에 이런 에러가 떠. 수정해줘. 에러 메시지"
* 상황 2: 화면은 나오는데 버튼을 눌러도 반응이 없다
* F12 → Console 탭 → 버튼을 다시 눌러본다 → 이때 빨간 메시지가 나타나는지 확인
* AI에게: "버튼을 클릭해도 아무 반응이 없어. 콘솔에 이런 에러가 떠. 에러 메시지 버튼 클릭 시 함수가 실행되도록 수정해줘."
* 상황 3: 기능은 되는데 디자인이 깨졌다
* AI에게: "기능 추가 후 디자인이 깨졌어. 기능은 유지하면서 디자인을 원래대로 복구해줘. 원래 디자인은 간단히 설명이었어."
* 상황 4: 에러 메시지를 못 찾겠다
* AI에게: "이 코드에서 문제가 있는 것 같은데 에러를 못 찾겠어. 코드를 검토해서 잠재적인 문제를 찾아서 수정해줘."
* 핵심: 에러 메시지를 직접 이해할 필요 없다! 그냥 통째로 복사해서 AI에게 보여주면 된다.
* 강사 유의사항: 에러를 만난 학생에게 "축하합니다! 에러를 만났네요. 이걸 해결하면 진짜 실력이 늘어요"라고 격려. 에러를 해결하는 과정 자체를 긍정적으로 만들어준다.
슬라이드 11 실습 1 — 콘솔 여는 법 시각 가이드 (실습 페이지)
* 크롬 브라우저에서 콘솔 여는 방법:
* 방법 1: 키보드에서 F12 키 누르기 → 오른쪽에 개발자 도구가 열림 → 상단에서 "Console" 탭 클릭
* 방법 2: Ctrl + Shift + J (윈도우/리눅스)
* 방법 3: 페이지 아무 곳에서 마우스 오른쪽 버튼 클릭 → "검사" → Console 탭

슬라이드 13 실습 2 — 추가 기능 & 재미 요소 (실습 페이지)
* 소요시간: 30분 (전반 15분)

* 추가 기능 아이디어 (원하는 것 골라서 도전):
* "다시하기" 또는 "초기화" 버튼: "결과 화면에서 '다시하기' 버튼을 누르면 처음 화면으로 돌아가게 해줘"
* 결과 공유 기능: "결과를 텍스트로 복사할 수 있는 '복사하기' 버튼을 추가해줘"
* 효과음/진동: "버튼 클릭 시 짧은 효과음이 나게 해줘" 또는 "결과가 나올 때 화면이 살짝 흔들리는 애니메이션을 넣어줘"
* 다크모드 토글: "오른쪽 상단에 해/달 아이콘 토글을 넣어서 다크 모드와 라이트 모드를 전환할 수 있게 해줘"
* 카운터/통계: "지금까지 몇 번 사용했는지 횟수를 화면에 표시해줘"
* 로컬 저장: "입력한 데이터가 브라우저를 닫아도 유지되게 localStorage에 저장해줘"
* 강사 유의사항: 핵심 기능 1개를 아직 완성 못한 학생은 추가 기능 없이 핵심 기능 완성에 집중하게 한다. "추가 기능은 보너스예요. 핵심이 되는 게 먼저!"
슬라이드 14 실습 2 — 전체 동작 테스트 (실습 페이지)
* 소요시간: 30분 (후반 15분)
* 목표: 앱을 처음부터 끝까지 사용해보며 문제가 없는지 확인
* 테스트 체크리스트 (활동지에도 포함):
* 앱을 처음 열었을 때 메인 화면이 정상으로 나타나는가?
* 핵심 기능 1이 동작하는가? (버튼 클릭 → 결과 표시)
* 핵심 기능 2가 동작하는가? (해당되면)
* 다시하기/초기화가 잘 되는가?
* 이상한 값을 넣었을 때(아무것도 안 넣고 버튼 클릭 등) 에러가 나지 않는가?
* 모바일 크기에서도 화면이 깨지지 않는가?
* 테스트 중 발견한 문제가 있으면:
* 문제 내용을 AI에게 설명: "아무것도 선택 안 하고 버튼을 누르면 에러가 나. 아무것도 선택하지 않으면 '먼저 선택해주세요'라는 안내 메시지가 뜨도록 수정해줘."
* 강사 멘트: "실제 앱 개발에서도 이렇게 '테스트'하는 과정이 꼭 필요해요. 만든 사람은 '이렇게 쓰겠지'라고 생각하지만, 사용자는 예상 못한 방식으로 쓰거든요. 그래서 '아무것도 안 넣고 버튼 누르기', '이상한 값 넣어보기' 같은 테스트가 중요합니다."
슬라이드 15 마무리 — 디버깅 무용담 & 성취감 공유 (강사용 교안)
* 소요시간: 10분
* 활동: "오늘의 디버깅 무용담" 공유
* 강사 멘트: "오늘 에러를 만난 사람 손 들어보세요. (거의 전원이 들 것) 축하합니다! 그리고 그 에러를 고친 사람? (대부분) 대단해요! 여러분은 오늘 '에러 → AI에게 보고 → 해결'이라는 실전 개발 사이클을 경험한 거예요."
* 2~3명에게 질문:
* "가장 황당했던 에러가 뭐였어요?"
* "AI가 고쳐준 과정이 신기했던 경험?"
* "직접 해결 방법을 찾아낸 적도 있었나요?"
* AI 리터러시 포인트: "오늘 배운 가장 중요한 것은 기술이 아니라 태도예요. '에러 = 실패'가 아니라 '에러 = AI와 대화할 주제'. 이 마인드셋은 AI를 쓸 때뿐 아니라 어떤 문제를 만나든 적용할 수 있어요."
* 강사 멘트: "여러분의 앱이 이제 진짜 동작합니다! 지난주만 해도 코드가 뭔지도 몰랐는데, 지금 버튼을 누르면 반응하는 앱을 가지고 있잖아요. 이게 바이브 코딩의 힘이에요."
