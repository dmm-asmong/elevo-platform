한 줄 정리

Skill은 재사용 가능한 작업 설명서입니다

AI에게 반복해서 설명하던
작업 순서와 기준을 저장한
재사용 가능한 작업 설명서다

비유로 이해하기

와플 기계와 반죽의 관계

틀(Skill)과 내용(주제)을 분리하면, 절차와 출력 형식을 더 일관되게 유지할 수 있습니다

매번 다시 설명
일반 프롬프트 복사·붙여넣기
매번 손으로 모양을 빚어 빵을 굽는 것과 같습니다.
매 대화마다 길게 설명해야 하고, 대화창의 기억 용량(컨텍스트)을 크게 낭비하며, 실행할 때마다 결과 품질이 들쭉날쭉해집니다.
틀은 유지하고 내용만 교체
Skill(도구화·모듈화)
AI에게 규격화된 '와플 기계(작업 틀)'를 꽂아주는 것과 같습니다.
딸기 반죽을 넣든 초코 반죽을 넣든(주제·대상이 바뀌어도), 항상 같은 규격(정확히 5장, 단일 HTML, 모바일 대응)을 더 안정적으로 유지할 수 있습니다.
Skill로 만들 것 · 만들지 않을 것

모든 반복이 Skill이 되는 건 아닙니다

🧠
대화 기억 절약 — 긴 규칙을 매번 대화창에 반복하지 않고, AI의 외장 도구함에 넣어 필요할 때만 호출합니다.
긴 지시를 매번 다시 넣을 때보다 규칙 누락 가능성을 줄일 수 있습니다.
⚠️
매번 다른 일은 Skill로 만들지 않습니다 — 오늘처럼 한 번만 하는 세부 요청(예: 지금 이 화면을 한 번 다듬어 달라는 부탁)은 Skill로 만들지 않고 직접 프롬프트로 처리합니다.
Skill은 "앞으로도 반복할 일"에만 만듭니다.
PART 2 Skill의 최소 구조

Skill에서 오늘 필요한 것만 봅니다

SKILL.md 한 장, 정확한 name과 description이면 충분합니다

Skill 폴더 구조

Skill 폴더에는 SKILL.md가 필수입니다

없으면 그건 그냥 메모장이지 Skill이 아닙니다

skill-name/ ├── SKILL.md 필수 — 이름·설명·작업 순서 │ ├── YAML frontmatter 필수: name, description │ └── 본문(Markdown) Skill이 실행될 때 AI가 읽는 지침 ├── agents/ 선택 — 화면에 어떻게 보여줄지 정보 ├── scripts/ 선택 — 매번 반복 실행할 코드 ├── references/ 선택 — 필요할 때만 꺼내 보는 참고 문서 └── assets/ 선택 — 완성본에 들어갈 재료 파일
오늘 만드는 Skill엔 필요한가?

실행에 필수인 것은 SKILL.md 한 장입니다

폴더 쉬운 뜻 오늘 필요한가?
SKILL.md 이름·설명·작업 순서를 적은 필수 파일 필수 — 이것만으로 실행 가능
agents/ 이 Skill을 목록·화면에 어떻게 보여줄지 정하는 정보 선택 — creator가 화면 표시용으로 만들 수 있음
scripts/ 매번 같은 코드를 새로 짜지 않도록 미리 저장해 두는 실행 코드 필요 없음
references/ 본문에 다 적기엔 길어서 필요할 때만 꺼내 보는 참고 문서 필요 없음
assets/ 지침이 아니라 완성본에 실제로 들어갈 재료 파일 필요 없음
name과 description 규칙

AI가 Skill을 찾아 쓰는 표지판입니다

description은 AI가 사용자의 요청을 읽고, 알맞은 Skill을 고를 때 참고하는 설명입니다

필드 규칙 확인 방법
name 소문자·숫자·하이픈만 사용, 64자 이내, 폴더 이름과 반드시 같아야 함 education-slide-maker처럼 폴더명 = name인지 대조
description 무엇을 하는지 + 언제 쓰는지 + 언제는 쓰면 안 되는지까지 담는다 14페이지의 좋은 예·나쁜 예와 비교
이름이 여러 개 보이는 이유

폴더명·name·display_name은 역할이 다릅니다

실행에 쓰는 이름과 화면에 보이는 이름을 나누어 관리합니다

구분 적는 곳 역할 예시
폴더명 Skill 폴더 파일을 저장하고 찾는 실제 위치 education-slide-maker/
name SKILL.md $이름으로 직접 호출하는 식별자 education-slide-maker
display_name agents/openai.yaml /skills 같은 화면에 보여 줄 이름 교육 슬라이드 메이커
🔎
폴더명과 name은 같게 맞춥니다. display_name은 사람이 읽기 좋게 달라도 됩니다.
description은 이름이 아니라, AI가 요청과 비교해 자동 호출 여부를 판단하는 설명입니다.
좋은 description · 나쁜 description

약병 라벨처럼 언제 쓰는지 명확해야 합니다

✅ 좋은 description
"교육 주제와 대상을 받아 자료 조사·5장 개요·승인 후 HTML 슬라이드 제작을 이어줄 때 사용한다."
무엇을(조사·개요·HTML), 언제(교육자료 요청 시) 쓰는지 드러남
❌ 나쁜 description
"교육 자료를 도와주는 스킬"
언제 쓰는지 알 수 없어 AI가 다른 요청에도 잘못 꺼낼 수 있다

기본 동작 확인
AI가 조사와 제작을 맡아도 세 지점은 사람이 결정합니다: ① 조사 내용이 대상·수준에 맞는가 ② 5장 흐름에서 빠지거나 불필요한 내용은 없는가 ③ 이 개요로 HTML을 만들어도 되는가

개요 단계의 수정은 지우개질 한 번입니다

HTML이 만들어진 뒤의 수정은 완공된 건물을 다시 뜯어고치는 공사입니다

📝
개요 단계 — 지우개질
짧은 텍스트 개요에서 내용을 고치는 것은 '건축 설계도에 연필로 지우개질하기'처럼 변경 범위가 작고 확인하기 쉽습니다.
🏗️
HTML 완성 후 — 대형 공사
수백 줄 코드가 완성된 뒤 "3번 슬라이드 주제 바꿔줘"라고 하면, AI가 CSS·JS·전환 구조를 다시 뜯어고치다가 멀쩡하던 버튼을 망가뜨리는 회귀 버그가 생길 위험이 커집니다.
🚪
그래서 코드를 작성하기 직전, 사람이 설계도를 최종 확정하는 '승인 검증 게이트'를 반드시 둡니다.

화면의 다섯 가지 요소를 정리합니다

새 UI 제작에도 쓸 수 있지만, 오늘은 기존 메인 화면 개선으로 범위를 제한합니다

개선 포인트 화면에서 보이는 변화
계층(hierarchy) 제목 > 본문 > 보조 문구 순서가 눈에 들어옴
타이포(typography) 글자 크기·줄간격이 읽기 쉬워짐
여백(spacing) 답답한 밀집이 풀리고 구역이 나뉨
대비(contrast) 글자와 배경이 뚜렷하게 구분됨
정렬(alignment) 카드·버튼이 한 줄로 맞춰짐
좋은 부탁 · 나쁜 부탁
