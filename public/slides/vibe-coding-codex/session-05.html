화면에서 입력한 정보가 오래 남으려면 가운데 전달 창구와 뒤쪽 저장소가 필요합니다.

개념 02

화면·처리·저장은 세 층으로 나뉩니다

한 파일 안에서 끝나던 웹앱이 여러 사람의 데이터를 공유하려면 뒤쪽 두 층이 필요합니다.

➔

Google Sheets에 여러 사람의 기록을 계속 보관
프론트엔드만으로 충분한 경우 백엔드·DB가 필요한 경우
타이머 · 계산기 · 퀴즈 · 랜덤 뽑기처럼

개념 03

Apps Script는 구글이 관리해 주는 백엔드입니다

앞 장의 가운데 처리 층을 직접 운영하지 않고도 사용할 수 있는 이유를 봅니다.

내가 하는 일
레시피에 해당하는 코드 작성

어떤 데이터를 받고, 시트의 어느 열에 저장하고, 무엇을 돌려줄지 정합니다.

Google이 하는 일
서버 실행과 운영 관리

컴퓨터 준비, 보안 업데이트, 용량 관리와 웹 주소 제공을 대신 처리합니다.

☁️
그래서 ‘서버리스(Serverless)’라고 부릅니다.
서버가 없는 것이 아니라, 내가 직접 관리할 서버가 보이지 않는 방식입니다.
개념 04

창구를 지키는 문지기 두 명

기록을 보낼 때와 다시 불러올 때, 데이터의 이동 방향이 반대입니다.

게임 화면기록 등록 · TOP 3 표시
doPost / doGet보내는 문 · 읽는 문
Google Sheets기록 저장 · 목록 제공
↔
doPost는 기록을 시트로 보내고, doGet은 저장된 기록을 화면으로 가져옵니다. 코드는 잠시 후 AI가 작성합니다.
개념 05

화면은 그대로 둔 채 조용히 배달합니다

🛵 배달앱 비유

배달앱으로 주문하면 배달원이 올 때까지 화면 앞에 서서 기다리지 않죠. 주문만 넣고 다른 일을 하다가 완료 알림을 받습니다.
게임도 똑같습니다 — [랭킹 등록]을 누르면 화면은 그대로인 채(새로고침 없이) 뒤에서 조용히 점수가 시트로 배달됩니다.

fetch는 무슨 뜻인가요?

브라우저가 다른 주소로 데이터를 보내거나 받아오는 기본 기능입니다. 영단어 뜻은 ‘가져오다’에 가깝지만, 코드에서는 보내기에도 사용합니다.

중복 배달 방지

배달 오는 중에 또 주문하면 같은 주문이 두 번 들어가겠죠.
전송하는 순간엔 버튼을 잠그고 전송 중... 표시를 띄웁니다.

💬
프롬프트에 fetch를 꼭 쓸 필요는 없습니다. “화면을 새로고침하지 않고 뒤에서 웹앱 주소로 데이터를 보내줘”라고 말하면 충분합니다. 구현 방식을 정확히 지정하고 싶을 때만 fetch를 덧붙입니다.

"화면이 안 떠요"

화면이 안 뜨는 게 아니라 원래 화면이 아닙니다.
식당 비유로 돌아가면, 이건 홀이 아니라 주방으로 통하는 배식구입니다.

이론 2 · 저장소 비교

저장소 무료 한도 초보자 관점 특징
Google Sheets + GAS ⭐오늘 선택 최대 1,000만 셀 진입장벽 제로 — 익숙한 스프레드시트 화면에서 데이터가 쌓이는 것을 직접 확인
Firebase Firestore 하루 쓰기 2만 건 구글의 정식 클라우드 DB. 보안 규칙(Rules)이라는 별도 문법 설계 필요

Airtable 베이스당 1,000개 UI는 예쁘지만 무료 행 수 한도가 작아 실습 중 금방 초과

더 큰 저장소도 있지만, 구글 시트는 지금 무엇이 쌓이는지 눈으로 직접 확인하기 쉽습니다.

복잡한 백엔드 관리자 콘솔을 오가지 않고 스프레드시트 셀 하나하나를 보며 디버깅할 수 있는 것이 초보자에게 가장 안전한 발판입니다.

🚨 브라우저의 기본 특성
HTML 소스코드는 누구나 뜯어볼 수 있습니다
  • 브라우저에서 F12를 누르면 코드 전문이 노출됨
  • JS 안에 관리자 비밀번호를 적어두면 즉시 유출
  • 클라이언트 코드는 보안 장벽이 되지 못한다
🛡️ 오후 실습의 안전 규칙

  • 홍길동, 5678 같은 가짜 데이터만 사용
  • 본인의 실제 휴대폰 번호 전체나 생년월일 입력 절대 금지
  • 혹시 입력했다면 즉시 구글 시트에서 해당 행 삭제
⚠️
"안 받으면 털릴 일도 없다." 수집 항목을 최소화하는 것이 소프트웨어 설계의 가장 확실한 보안 원칙입니다.
이론 2 · 실전 수칙

AI에게 코드를 맡길 때 지켜야 할 보안 2대 규칙

이 두 가지 원칙만 기억 보안 사고 예방

보안 원칙 AI에게 지휘할 때 쓰는 말 개념
비밀번호 하드코딩 금지 "비밀번호나 API 키는 자바스크립트 코드 안에 직접 쓰지 마" 코드 안에 중요 키를 적어두면 F12로 누구나 열람 가능. 절대 화면 코드에 노출하지 않음
개인정보 최소 수집 "서비스에 꼭 필요한 항목만 받고, 불필요한 개인정보는 입력창에서 제외해줘" 오전 랭킹에 실명 대신 닉네임만 받은 것이 바로 이 원칙의 실물 사례. 안 받으면 유출될 위험도 없음
💡 든든한 보안의 시작

Google Apps Script 웹앱은 실행 권한(나)과 접근 권한(모든 사용자)이 분리되어 있어, 방문자가 내 구글 계정이나 스프레드시트 원본 파일에 직접 침투하지 못하도록 구글 서버가 중간 방패 역할을 해줍니다.

📱 스마트폰 실행 3단계
  • 폰 브라우저 주소창에 내Vercel주소/game.html 입력
  • 게임을 한 판 플레이하고 닉네임을 넣어 [랭킹 등록] 클릭

⚠️ 폰 접속 시 확인사항
  • 카카오톡에서 열리지 않거나 동작이 불안정하면 Safari 또는 Chrome에서 다시 열기
  • 구글 로그인이 나오면 Apps Script의 실행: 나 · 액세스: 모든 사용자 · /exec 주소 확인
  • 등록 완료 메시지 확인 → PC 시트 새로고침 → 계속 안 되면 Apps Script 실행 기록 확인
  • Vercel 주소는 PC와 같은 Wi-Fi가 아니어도 접속 가능
🎉 3일차 숙제의 완결

하지만 시트는 하나였습니다. 여러분은 동네 오락실 게임기를 여러 기기에서 함께 사용하는 온라인 서비스로 확장했습니다.

Q1. 3일차 localStorage와 오늘 구글 시트는 무엇이 결정적으로 달랐나요?

➔ localStorage는 내 브라우저 서랍에만 갇혀 있었지만, 구글 시트는 스마트폰이든 다른 컴퓨터든 한곳에 데이터가 모였습니다.

➔ 거기는 사람이 보는 화면이 아니라, 데이터를 접수하고 돌려주는 API 창구였기 때문입니다. 화면과 데이터는 분리되어 있습니다.

Q3. 오늘 같은 절차를 두 번(게임 ➔ 출결) 했는데 무엇을 얻었나요?

➔ 소재가 바뀌어도 5단계(시트➔코드➔배포➔주소확인➔전송)는 똑같다는 걸 배웠습니다. 이제 어떤 웹앱이든 시트에 연결할 수 있습니다.
